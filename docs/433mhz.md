# 433 MHz on the RM4 Pro (experimental)

Part of [ESPHome-Broadlink-RM4](../README.md). The 433 MHz radio of the
RM4 Pro is **experimental**: the component is written from a flash dump of the
stock firmware. The module answers and frames are received on a device, sending
is not confirmed yet. Infrared is unaffected, the radio is a separate, optional
package.

## Switching it on

Add [`rf.yaml`](../esphome-broadlink-rm4-remote-firmware/devices/rm4-pro/rf.yaml)
to the package list of your [`rm4-pro.example.yaml`](../rm4-pro.example.yaml)
(the line is there, commented out) and keep `firmware_ref` and `ref` equal.
Then reflash over the air. The log of the device should now show:

```text
[bl3361] Listening on 433.920 MHz
```

If it says `The RF module does not answer on the UART` instead, see
[Troubleshooting](troubleshooting.md).

The carrier defaults to 433.92 MHz, set `rf_frequency` in your config for
something else (305-340 MHz and 430-440 MHz are possible). It only decides the
first start: once you pick a frequency in Home Assistant, that one is kept over
restarts, see [Choosing the frequency](#choosing-the-frequency).

## What you get in Home Assistant

| What | Name | Use |
|---|---|---|
| Select | RF Frequency | The frequency of the radio, see [Choosing the frequency](#choosing-the-frequency). |
| Event | `esphome.<name>_rf_received` | Fired for every received code. `code` holds the pulse timings in microseconds (positive = signal on, negative = off), `pulses` their number and `frequency_mhz` the frequency it was heard on. Watch it under **Developer tools → Events**. All values are text. |
| Event | `esphome.<name>_rf_learn` | Steps of a search or learning session, see [Learning a remote](#learning-a-remote-like-the-broadlink-app). |
| Action | `rf_learn` | Learns a remote like the Broadlink app does: hold a key, then press it briefly. |
| Action | `rf_find_frequency` | Only the first half of it: finds the frequency of a transmitter and tunes to it. |
| Action | `rf_cancel` | Ends a search or learning session. |
| Action | `rf_send_raw` | Sends a code: `code` is the list from the event, `repeat` how often (1-30). |
| Action | `rf_send_raw_at` | The same on another `frequency_mhz`, for this code only. |
| Action | `rf_set_frequency` | `frequency_mhz`, for example `315.0` or `433.92`. |
| Action | `rf_scan` | Logs the relative signal strength of 20 channels around the frequency. |
| Sensor | RF Signal Strength | Diagnostic, a raw relative value that rises with the signal. |

Example: switch a 433 MHz socket with a code you received before.

```yaml
action: esphome.broadlink_rm4_pro_rf_send_raw
data:
  repeat: 8
  code: [350, -1050, 1050, -350, 350, -1050, 350, -10850]
```

Learning is done by pressing the original remote next to the RM4 Pro and
copying `code` out of the event. Press the remote a few times: one clean frame
repeats, noise does not.

## Choosing the frequency

The entity **RF Frequency** shows the frequency of the radio and changes it.
Its options come from the configuration, `315 MHz` and `433.92 MHz` by default;
put your own in `rf.yaml` or in your config:

```yaml
bl3361:
  frequency_select:
    name: RF Frequency
    options: [315MHz, 433.92MHz, 433.42MHz]
```

- The choice is kept over restarts (`restore_value: false` switches that off).
  So `rf_frequency` only decides the very first start, and a change of it does
  nothing afterwards: pick the frequency in Home Assistant once.
- **Custom** appears when the radio sits on a frequency that is not in the list,
  for example after `rf_learn` found one or after `rf_set_frequency`. Choosing it
  does nothing.
- The radio listens on one frequency at a time. Switching back and forth hears
  only what is sent while it listens there. It tunes in a few hundredths of a
  second, so a short automation on a timer works, but a signal that comes in
  between is missed.
- To send on another frequency without moving the radio, use `rf_send_raw_at`:
  it tunes for this code and goes back to the selected frequency afterwards.
- The module tunes to 305-340 MHz and 430-440 MHz in steps of 10 kHz around 315
  and 433 MHz and 100 kHz elsewhere. 868 MHz is not possible.

## Learning a remote like the Broadlink app

The Broadlink integration of Home Assistant learns an RF remote in two steps:
`remote.learn_command` with `command_type: rf` first asks to **hold** a key (the
device sweeps the frequencies and finds the one the remote uses) and then to
**press it briefly** (the device stores the code). The stock firmware of the RM4
Pro does exactly that, and so does the action `rf_learn`:

1. **Sweep.** The radio listens its way through both bands: 305-340 MHz in
   500 kHz steps and 430-440 MHz in 500 kHz steps, the same requests the stock
   firmware builds. The channel that stands out of the average is refined in
   100 kHz steps and, around 315 and 433 MHz, in 10 kHz steps. Hold the key
   close to the device until the phase `capture` arrives. It gives up after
   30 s.
2. **Capture.** The radio stays on the frequency it found. Press the key briefly,
   a few times. A signal that comes back twice (within 25 % tolerance) counts as
   the code, noise never repeats. It gives up after 20 s.

The progress arrives as the event `esphome.<name>_rf_learn` with `phase`
(`sweep`, `found`, `capture`, `learned`, `timeout`, `cancelled` or `failed`),
`frequency_mhz`, `repeats` and `code`. This automation shows the steps like the
Broadlink integration does, and gives you the finished action to paste:

```yaml
automation:
  - alias: RF learning
    triggers:
      - trigger: event
        event_type: esphome.broadlink_rm4_pro_rf_learn
    variables:
      d: "{{ trigger.event.data }}"
    actions:
      - action: persistent_notification.create
        data:
          notification_id: rf_learn
          title: Learn an RF code
          message: >-
            {% if d.phase == 'sweep' %}
              Hold a key of the remote close to the RM4 Pro.
            {% elif d.phase == 'capture' %}
              Frequency found: {{ d.frequency_mhz }} MHz.
              Now press the key briefly, a few times.
            {% elif d.phase == 'learned' %}
              Learned on {{ d.frequency_mhz }} MHz, seen {{ d.repeats }} times.
              Paste this into a script or a switch:

                  action: esphome.broadlink_rm4_pro_rf_send_raw_at
                  data:
                    frequency_mhz: {{ d.frequency_mhz }}
                    repeat: 8
                    code: [{{ d.code }}]
            {% elif d.phase == 'timeout' %}
              Nothing found. Try again, closer to the device.
            {% elif d.phase == 'cancelled' %}
              Cancelled.
            {% elif d.phase == 'failed' %}
              The RF module does not answer, see the log of the device.
            {% endif %}
```

Start it with the action `esphome.broadlink_rm4_pro_rf_learn` (a button or a
script, for example); `esphome.broadlink_rm4_pro_rf_cancel` stops it. A learned
code goes into your own scripts, switches and buttons, for instance:

```yaml
template:
  - switch:
      - name: Socket living room
        unique_id: rf_socket_living_room
        turn_on:
          - action: esphome.broadlink_rm4_pro_rf_send_raw_at
            data:
              frequency_mhz: 433.92
              repeat: 8
              code: [350, -1050, 1050, -350, 350, -1050, 350, -10850]
        turn_off:
          - action: esphome.broadlink_rm4_pro_rf_send_raw_at
            data:
              frequency_mhz: 433.92
              repeat: 8
              code: [350, -1050, 350, -1050, 350, -1050, 350, -10850]
```

A rolling code (car keys, garage doors, alarms) changes with every press, so it
is never seen twice and cannot be learned this way, which is as it should be.

How close this is to the original is worth knowing:

| | Broadlink firmware and integration | This firmware |
|---|---|---|
| Finding the frequency | Sweep in 500 kHz steps with two requests, then refined in rounds | The same two requests, then refined in 100 kHz and 10 kHz steps; `sweep_margin` sets how clearly a channel has to stand out |
| Taking a code | Collects frames, keeps one that repeats | Collects frames, keeps one that repeats |
| Code format | A compressed binary packet in `.storage` | The raw timings, readable and editable |
| Storage | The integration, per device and command | Your scripts and switches in Home Assistant |
| Sending | `remote.send_command` | `rf_send_raw` / `rf_send_raw_at` |

The sweep is a re-implementation from the description of the stock code, not a
copy; its constants (how far a channel has to stand out) were chosen from the
readings of a real device, where the quiet band sits around 20-23 and a remote
at close range reaches about 26. If the sweep finds nothing although the remote
is close, lower `sweep_margin` (default 3) in the `bl3361:` section.

## Noise

The receiver of the module has no squelch. Right after the module is tuned it
produces a burst of random pulses for about a second, and these look like
frames. Everything in the first 1.5 s after tuning is dropped now
(`settle_time`, set it to `0s` to switch that off). Further noise is rare, a
real signal has more pulses and they repeat. Raise `min_pulses` (default 24)
to just below the number of pulses of your remote if events fire for noise, and
check `pulses` in your automations: a value in an event is text, so compare
`trigger.event.data.pulses | int`.

## HAIR, the Broadlink integration and Home Assistant's radio frequency platform

- **HAIR** is for infrared only. It talks to Home Assistant's `infrared` platform
  and its Sniffer captures IR, so it cannot learn an RF code. The project lists
  RF devices as an open request ([HAIR issue 4](https://github.com/DAB-LABS/HAIR/issues/4)).
  Use `rf_learn` and your own scripts for RF.
- The **Broadlink integration** learns and sends RF through its `remote` entity
  while the RM4 Pro runs the Broadlink firmware. With this firmware it is
  `rf_learn` and `rf_send_raw_at` instead, see the table above.
- Home Assistant 2026.5 added a native **Radio frequency** platform, an entity
  that represents a sub-GHz transmitter for device integrations (the release
  notes name a Honeywell string lights and a Novy cooker hood integration, and
  the RM4 Pro through the Broadlink integration). It only sends. ESPHome has an
  experimental `radio_frequency` entity for it, which this firmware does not
  offer yet: the interface is marked experimental and may change at any time.
  Until then those integrations cannot use an RM4 Pro that runs this firmware.

## Testing without owning a 433 MHz device

Nobody has to own a 433 MHz device to try this. You need a signal source, and
all of these are cheap:

| Source | Cost | Notes |
|---|---|---|
| Fixed-code key fob (EV1527 / PT2262 type) | a few euros | The simplest signal there is; ideal for the first test. |
| 433 MHz wireless sockets or a doorbell (Intertechno, Brennenstuhl, Smartwares and similar) | 10-20 euros | Also gives you something to switch when you test transmitting. |
| Weather station or outdoor sensor | often at home already | Transmits on its own every few seconds to minutes. |
| ESP32 or ESP8266 with an FS1000A transmitter module | about 3 euros | Programmable signal source, see below. |

For an independent view of what is on the air, and to tell your RM4 Pro from
your signal source, use one of these:

- **RTL-SDR stick** (about 30 euros) with [rtl_433](https://github.com/merbanan/rtl_433).
  `rtl_433 -f 433.92M -A` decodes known protocols and analyzes unknown ones.
  This is also the best way to see what the RM4 Pro itself transmits.
- **A second ESP32** with a receiver module (RXB6 or SRX882, about 5 euros)
  running ESPHome's `remote_receiver`, which prints raw timings of anything it
  hears:

  ```yaml
  remote_receiver:
    pin:
      number: GPIO4
      inverted: false
    dump: raw
    # 433 MHz receivers output constant noise without a signal.
    tolerance: 25%
    filter: 100us
    idle: 10ms
  ```

- **Flipper Zero** or similar: the Sub-GHz *Frequency Analyzer* and *Read RAW*
  show the frequency and the raw signal.
- **The stock firmware as a baseline.** Before you flash ESPHome, learn your
  signal source with the Home Assistant Broadlink integration (`remote.learn_command`
  with `command_type: rf`). If that works, the source and the hardware are fine;
  the code it stores is also a reference for what the ESPHome component should
  see.

To check that an RM4 Pro running ESPHome hears the same thing, hold the remote
about 10 cm from the device, press it a few times and compare the event with
the output of the SDR or the ESP32.

## Finding out what is on the air

Out of curiosity, or to find out what a device uses before you buy a matching
receiver:

| What | Tool | How |
|---|---|---|
| Is it 433.92 MHz, 315 MHz or 868 MHz? | RTL-SDR with SDR++ or GQRX | Look at the waterfall while pressing the button; the frequency of the burst is the answer. |
| Which protocol? | rtl_433 | `rtl_433 -f 433.92M -f 868.3M -H 30` hops between bands; `-F json` logs every decoded device. Hundreds of weather stations, remotes, doorbells and tyre pressure sensors are known. |
| Unknown signal | Universal Radio Hacker, `rtl_433 -A` | Records the raw signal and finds the bit timing and the encoding. |
| Weak or occasional transmitters | `rf_scan` action of the RM4 Pro | Shows the relative strength per channel; press the remote while it runs. The window is 200 kHz wide around 433.92 MHz, move it with `rf_set_frequency`. |
| Other smart home devices | Router client list, `esp32_ble_tracker` (Bluetooth), a Zigbee sniffer | Wi-Fi and Bluetooth devices announce themselves; Zigbee and Z-Wave need a sniffer for their bands (2.4 GHz and 868 MHz). |

The RM4 Pro cannot hear 868 MHz: its radio only tunes to 305-340 MHz and
430-440 MHz. 315 MHz (North America, Asia) and 433.92 MHz (Europe) are both
possible.

## Reading a Smartwares or other remote

Many 433 MHz sockets, doorbells and remotes of brands like Smartwares,
Intertechno, KlikAanKlikUit and Brennenstuhl use simple fixed codes on 433.92 MHz
with on/off keying (some Smartwares products use other frequencies, so confirm
it with an SDR first). That is exactly what the component is built for. If the
code changes with every press (a *rolling code*, found in car keys, garage doors
and alarms), it can be received but not replayed, and should not be.

A good first session once you have the device:

1. Check the frequency with an RTL-SDR, or run `rf_scan` while you press the remote.
2. Press the remote five times next to the RM4 Pro and look at the events.
3. Compare the pulse lengths with a second source (SDR or ESP32).
4. Send the code back with `rf_send_raw` to a socket that is meant to be switched.

## Rules for transmitting

Receiving is passive and uncritical. Transmitting is regulated:

- Transmit only in the license-free ISM band (433.05-434.79 MHz in Europe) and
  stay within the low-power limits and duty-cycle rules of your country. The RM4
  Pro itself is built for that.
- The component allows up to 30 repetitions and 2048 pulses per code; that is a
  technical limit, not a legal one.
- Do not replay codes of devices that protect something: cars, garage doors,
  alarm systems, door locks. That is illegal in most places and rolling codes
  would not work anyway.
